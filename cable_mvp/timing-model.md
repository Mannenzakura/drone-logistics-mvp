# 时间片模型（复核版）

## 10. 时间片编队同步：等待、容量与成本

实现为 experiments.mjs 的 formationTiming 与 Python formation_studies.py。浏览器在可终止 Worker 中计算，输入修改后点击“计算时间片方案”；失败保留上次结果。支持 1–48 片、总计至多 240 架次，超过范围会明确提示。JSON 导出含参数、全部情景状态、目标值和逐片计划。

单走廊、同质载重，n_t 架在片 t 起点就绪。w_(t−1) 为上片结转，f_t 为本片起飞，w_t 为本片末等待；w_0=0、w_T=0：

```text
w_(t−1) + n_t = f_t + w_t
f_t = Σ_m m y_(t,m)，y_(t,m) 为非负整数
Σ_m [D+(m−1)δ] y_(t,m) ≤ capacity_per_slice
关闭等待时，所有 w_t=0
```

D 是单机等效占用，δ 是每新增编队成员的等效增量，须满足 0<δ≤D。每片容量是外生等效通行占用预算；不能未经流量/速度/时间换算就当作实际走廊瞬时长度或机场服务率。

每架单飞巡航 E_solo=(k0+k1·payload)·distance。m 机编队的巡航电量 E_solo[1+(m−1)γ]，一架领航不打折，γ 暂为所有跟随机的固定输入，不随 m 重新计算。协调费按每支 m≥2 的编队计一次。每架跨一片等待的费用为 time_value·payload·slice_minutes + loiter·energy_price·k0·speed/60·slice_minutes。

三情景：全单飞且等待同样计费；可编队但等待免费（乐观成本下界）；可编队且等待计费。三者遵守同一需求、容量、允许等待开关与末片清零条件，每个情景独立报告可行性。单飞不可行时仍展示可行的编队方案，成本差额及比例记为不可比较而不是零。

算法先对起飞总数 f 与分组数 g 做背包预计算，利用占用恒等式 fδ+g(D−δ) 选出容量可行的最低发车成本，再用片间动态规划处理结转。没有枚举所有整数划分；在明示规模范围内是所列离散模型的全局最优，使用浮点比较容差 1e−12。它不是全网连续时间模型的最优性证明，也不是一般线性规划的直接替代。

默认示例：全单飞成本 183.75，编队免费等待 167.825，编队等待计费 169.05。成本节省从 15.925 减少到 14.70，缩减约 7.69%。这是电费、时效与协调费的合计差额，不能称为纯“节能率”。仅在基准与两个比较方案均可行且理想成本节省为正时计算缩减比例。

逐片表给出新到、上片结转、单飞、各支编队规模、起飞数、等待数、预算占用与成本。程序独立核验库存守恒、末片清零、容量和账本相加；小规模结果与完整穷举比较，并与 Python 做跨实现对比。

## 10.1 逐机资源约束（2026-09-26 新增）

上一版把「调度可行」直接写成结论，但并没有约束逐机电池和累计等待时长，也没有机场服务率。本版补上四项，**每项填 0 都表示本情景不施加该约束**，因此默认参数下的数字与上一版一致。

```text
电池：      wait_t · E_wait + E_cruise ≤ battery_kwh
空中时长：  wait_t · slice_minutes + distance/speed·60 ≤ max_airborne_min
等待上限：  wait_t ≤ max_wait_slices
机场服务率：departed_t ≤ service_per_slice
```

其中 `E_wait = loiter·k₀·speed/60·slice_minutes` 是每片等待耗能，`E_cruise` 取**领航不打折**的单机巡航能耗作为队内上界（对跟随机偏保守，已在返回值里写明）。

**关键实现点：等待上限不需要进状态。** 「每架最多等 W 片」在 FIFO 下发派等价于一条纯聚合约束

```text
carried_t ≤ Σ_{s = t−W+1}^{t} n_s        （最近 W 片的到达数之和）
```

理由是：FIFO 下被结转的飞机必定是「最年轻的」那些，所以「谁都等不超过 W 片」当且仅当被结转载量不超过最近 W 片新到的总量。因此动态规划的状态仍然只有「结转载量」一个维度，状态空间与上一版同一量级；程序另外用一个 FIFO 队列把聚合方案还原成逐机序列，**独立复核实际最长等待**并写进 `realized_max_wait_slices`。

三个情景（全单飞、编队免费等待、编队计费等待）**共用同一套物理约束，只有等待是否计费不同**——否则比较就不公平了。若资源不足以执行，三个情景一起报 `resource_infeasible` 并给出具体原因（例如「电池 4 kWh 不足以完成一次含等待的 70 km 架次」），而不是悄悄返回一个不可行的成本。

程序还会再解一次**不加任何逐机资源上限**的同一问题作对照，写进 `resource_cap_effect`：`binding` 为 false 时说明这些上限在本情景下没有改变结果。默认情景（每片需求都能当片清空）就是这种情况，所以四个参数填 0 或填一个宽松值得到的数字完全相同。

**一个值得注意的量级。** 默认片长 60 min、k₀=0.025、巡航 108 km/h 时，每片等待耗能 2.7 kWh，而 70 km、10 kg 的单机巡航只要 4.083 kWh——**盘旋一整片的代价超过航段本身耗能的一半**。所以电池约束在默认参数下几乎是「要么不能等，要么可以等很多」的二值行为：4 kWh 直接不可行，8 kWh 已允许等待 1 片。

## 10.2 本模块仍未覆盖

- 多段航路、充电闭环、卡车接驳；
- 逐机电池的**衰减与充电排队**；本版只检查「等待 + 一次巡航 ≤ 电池」，不含充放电效率与温度影响；
- 机场跑道的真实占用冲突，以及把「每片服务能力」标定成真实起降服务率所需的机型与场地数据；
- 因此「资源可行」仍然不等于「可以实际执行」，只是比上一版多排除了三类明显不可行的调度。
